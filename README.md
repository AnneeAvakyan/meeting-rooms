# Переговорка — сервис бронирования переговорных комнат

REST API на Go для управления переговорными комнатами и их бронированием.

Сервис позволяет сотрудникам просматривать переговорные, находить свободные помещения, создавать, изменять и отменять собственные бронирования. Администраторы дополнительно могут создавать переговорные комнаты.

Реализованы JWT-аутентификация, разграничение доступа по ролям и проверка пересечений бронирований по времени.
[![Go Tests](https://github.com/AnneeAvakyan/meeting-rooms/actions/workflows/go-tests.yml/badge.svg)](https://github.com/AnneeAvakyan/meeting-rooms/actions/workflows/go-tests.yml)

## Функциональность

### Управление пользователями

- Регистрация новых пользователей
- Авторизация по email и паролю
- Безопасное хранение паролей с использованием bcrypt
- JWT-аутентификация с ограниченным временем действия токена
- Разграничение доступа по ролям `employee` и `admin`
- Автоматическое назначение роли `employee` при регистрации

### Управление переговорными

- Просмотр списка переговорных комнат
- Хранение параметров переговорных: название, вместимость, оборудование
- Создание новых переговорных администратором
- Поиск свободных переговорных на заданный временной интервал
- Просмотр календаря активных бронирований конкретной комнаты

### Управление бронированиями

- Создание бронирования от имени авторизованного пользователя
- Изменение времени и комнаты собственного бронирования
- Отмена собственного бронирования
- Запрет изменения и отмены чужих бронирований
- Проверка корректности временного интервала
- Проверка пересечений с существующими активными бронированиями
- Логическая отмена бронирований (`status = cancelled`)
- Исключение отменённых бронирований из календаря занятости

При создании бронирования идентификатор пользователя определяется по JWT, а не передаётся клиентом в теле запроса.

## Архитектура

Приложение разделено на несколько логических слоёв:

- **HTTP layer** — маршрутизация, обработчики HTTP-запросов, валидация входных данных, middleware и формирование ответов.
- **Service layer** — бизнес-логика регистрации, авторизации и работы с пользователями.
- **Repository layer** — интерфейсы доступа к данным и их реализации для PostgreSQL.
- **Domain layer** — модели пользователей, комнат и бронирований.
- **Auth** — создание и проверка JWT.
- **Config** — загрузка конфигурации приложения.

Бизнес-логика отделена от HTTP-обработчиков и конкретной реализации базы данных с помощью интерфейсов репозиториев.

## Запуск проекта

### Требования

- Docker
- Docker Compose

### 1. Настройка окружения

Создайте файл `.env` на основе примера конфигурации:

```bash
cp .env.example .env
```

Заполните необходимые переменные окружения для подключения к PostgreSQL и настройки JWT.

Для генерации секретного ключа JWT можно использовать:

```bash
openssl rand -hex 32
```

Полученный ключ необходимо указать в переменной `SECRET_KEY`.

Не следует использовать предсказуемые секреты или публиковать `.env` в репозитории.

### 2. Запуск приложения

```bash
docker compose up -d --build
```

После запуска HTTP API доступен по адресу:

```text
http://localhost:8080
```

### 3. Проверка работоспособности

```bash
curl -i http://localhost:8080/healthz
```

Для просмотра логов:

```bash
docker compose logs -f
```

## API

### Публичные эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/healthz` | Проверка работоспособности |
| `POST` | `/auth/register` | Регистрация пользователя |
| `POST` | `/auth/login` | Авторизация, получение JWT |

### Защищённые эндпоинты

| Метод | Путь | Описание | Доступ |
|---|---|---|---|
| `GET` | `/rooms` | Список комнат | Employee, Admin |
| `GET` | `/rooms/available?from=&to=` | Поиск свободных комнат | Employee, Admin |
| `GET` | `/rooms/{id}/active` | Календарь активных бронирований комнаты по ID| Employee, Admin |
| `GET` | `/rooms/{id}/calendar` | Архив всех бронирований комнаты по ID| Employee, Admin |
| `POST` | `/rooms` | Создание комнаты | Admin |
| `POST` | `/bookings` | Создание бронирования | Employee, Admin |
| `PUT` | `/bookings/{id}` | Изменение собственной брони | Владелец |
| `DELETE` | `/bookings/{id}` | Отмена собственной брони | Владелец |

Для доступа к защищённым эндпоинтам необходим JWT в заголовке:

```http
Authorization: Bearer <access_token>
```

## Примеры использования

### Регистрация пользователя

```bash
curl -i -X POST http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "Anna",
    "email": "anna@example.com",
    "password": "securePassword123"
  }'
```

Успешный ответ: `201 Created`.

```json
{
  "id": 1,
  "name": "Anna",
  "email": "anna@example.com",
  "role": "employee"
}
```

### Авторизация

```bash
curl -i -X POST http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "anna@example.com",
    "password": "securePassword123"
  }'
```

Успешный ответ: `200 OK`.

```json
{
  "token": "<access_token>",
  "token_type": "Bearer"
}
```

В следующих примерах предполагается, что полученный JWT сохранён в переменной окружения `TOKEN`.

### Просмотр переговорных

```bash
curl -i http://localhost:8080/rooms \
  -H "Authorization: Bearer $TOKEN"
```

### Создание переговорной

Доступно только пользователю с ролью `admin`.

```bash
curl -i -X POST http://localhost:8080/rooms \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "name": "Meeting Room A",
    "capacity": 8,
    "equipment": "Projector, Whiteboard"
  }'
```

Успешный ответ: `201 Created`.

### Создание бронирования

```bash
curl -i -X POST http://localhost:8080/bookings \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "room_id": 1,
    "start_time": "2026-11-18T10:00:00+03:00",
    "end_time": "2026-11-18T11:00:00+03:00"
  }'
```

Успешный ответ: `201 Created`.

Поле `user_id` передавать не требуется — оно определяется сервером по токену.

Время необходимо передавать в формате RFC3339 с указанием часового пояса.

### Изменение бронирования

```bash
curl -i -X PUT http://localhost:8080/bookings/1 \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "room_id": 2,
    "start_time": "2026-11-18T12:00:00+03:00",
    "end_time": "2026-11-18T13:00:00+03:00"
  }'
```

Изменить бронирование может только его владелец. Отменённые бронирования не подлежат изменению.

### Отмена бронирования

```bash
curl -i -X DELETE http://localhost:8080/bookings/1 \
  -H "Authorization: Bearer $TOKEN"
```

Успешный ответ: `204 No Content`.

Бронирование не удаляется физически из базы данных — его статус меняется на `cancelled`.

### Просмотр календаря комнаты

```bash
curl -i http://localhost:8080/rooms/1/calendar \
  -H "Authorization: Bearer $TOKEN"
```

Календарь содержит только активные бронирования.

Если комната существует, но не имеет активных бронирований, возвращается `200 OK` и пустой массив `[]`.

Если комната не существует — `404 Not Found`.

## Правила бронирования

Для предотвращения некорректных бронирований реализованы следующие ограничения:

1. Время начала должно быть раньше времени окончания.
2. Бронирование привязывается к существующей переговорной.
3. Активные бронирования одной комнаты не должны пересекаться по времени.
4. Смежные интервалы допускаются: окончание одной встречи может совпадать с началом следующей.
5. Отменённые бронирования не участвуют в проверке пересечений.
6. Изменять и отменять бронирование может только его владелец.
7. Отменённую бронь нельзя изменить или отменить повторно.

Проверка пересечений выполняется как на уровне приложения, так и в PostgreSQL-репозитории. При создании и изменении используются транзакции и блокировки записей для снижения риска конфликтующих операций.

## Коды ответов HTTP

| Код | Значение |
|---|---|
| `200 OK` | Успешное получение или изменение данных |
| `201 Created` | Пользователь, комната или бронирование созданы |
| `204 No Content` | Бронирование отменено |
| `400 Bad Request` | Некорректные входные данные |
| `401 Unauthorized` | Отсутствует или недействителен JWT, неверные учётные данные |
| `403 Forbidden` | Недостаточно прав или попытка изменить чужую бронь |
| `404 Not Found` | Ресурс не найден либо недоступен для данной операции |
| `409 Conflict` | Конфликт бронирований или email уже зарегистрирован |
| `500 Internal Server Error` | Внутренняя ошибка сервера |

## Тестирование

Проект содержит автоматизированные тесты бизнес-логики и основных компонентов REST API.

Проверяются:

- Валидация временных интервалов и пересечения бронирований.
- Учёт отменённых бронирований и обновления существующих.
- Регистрация пользователей, хэширование паролей и авторизация.
- Генерация и проверка JWT.
- Проверка прав доступа через middleware.
- HTTP-обработчики комнат и бронирований.

### Локальный запуск

Запуск всех тестов:

```bash
go test ./...
```

Запуск с подробным выводом:

```bash
go test -v ./...
```

Проверка покрытия:

```bash
go test -cover ./...
```

Проверка гонок данных:

```bash
go test -race ./...
```

### Continuous Integration

Для проекта настроен GitHub Actions workflow, который автоматически запускается при `push` и создании или обновлении `pull request`.

CI выполняет тесты с проверкой гонок данных и сборку Go-приложения. Результаты доступны во вкладке **Actions** репозитория.

Unit-тесты не требуют запущенной PostgreSQL, поскольку внешние зависимости подменяются тестовыми реализациями.
